\subsection{Fundamentos de la Virtualización Ligera}

 La virtualización ligera es un término empleado para hacer referencia a diferentes alternativas a la virtualización tradicional basada en hipervisores de tipo 1 y tipo 2, orientadas principalmente a la ejecución de aplicaciones y servicios con un menor overhead de recursos. Estas alternativas surgen como respuesta al desplazamiento progresivo de la carga computacional de las aplicaciones y servicios hacia entornos de computación en la nube, lo que ha provocado un cambio de paradigma en la forma de desplegar y ejecutar las aplicaciones. Este cambio ha favorecido la evolución desde arquitecturas monolíticas hacia arquitecturas basadas en microservicios, en las que las aplicaciones se dividen en componentes independientes que pueden ser desplegados y gestionados de forma individual.

 En este sentido, la virtualización basada en hipervisor requiere generalmente un mayor tiempo de arranque y un mayor consumo de recursos, principalmente debido a la necesidad de ejecutar una máquina virtual que incluye un sistema operativo completo, junto con su propio kernel, librerías y controladores necesarios para interactuar con el hardware virtualizado. Por este motivo, han surgido alternativas como los contenedores y los \textit{unikernels} o \textit{Library OS}, que buscan reducir el overhead asociado a la virtualización tradicional y mejorar el aprovechamiento de los recursos disponibles. Estas tecnologías resultan especialmente interesantes en entornos donde se requiere desplegar un elevado número de servicios de forma rápida y con un consumo reducido de recursos \cite{vm-vs-docker-unikernels}.

 En el caso de los \textit{containers}, se emplean diferentes mecanismos proporcionados por el kernel de Linux para aislar y gestionar los procesos. Entre ellos destacan los \textit{namespaces}, que permiten proporcionar espacios de ejecución aislados para diferentes recursos del sistema, y los \textit{cgroups}, que permiten controlar y contabilizar el uso de recursos como CPU, memoria o entrada y salida de los procesos. A diferencia de las máquinas virtuales, los contenedores no requieren un sistema operativo completo para cada instancia, sino que utilizan el kernel del sistema operativo anfitrión. Las aplicaciones y sus dependencias se distribuyen mediante \textit{imágenes}, que generalmente presentan un tamaño inferior al de las imágenes de máquinas virtuales al no incluir un sistema operativo completo.

 Los contenedores también proporcionan mecanismos para aislar diferentes componentes del sistema. Por ejemplo, mediante las funcionalidades de red proporcionadas por Linux es posible crear redes virtuales independientes y controlar la comunicación entre contenedores y con el sistema anfitrión. Asimismo, los mecanismos de almacenamiento proporcionan la posibilidad de utilizar \textit{volúmenes} para mantener datos persistentes independientemente del ciclo de vida de los contenedores.

 En cuanto a la seguridad, los contenedores presentan un nivel de aislamiento diferente al proporcionado por la virtualización mediante hipervisor. Al compartir el kernel del sistema operativo anfitrión, un contenedor no dispone de un kernel independiente, por lo que una vulnerabilidad en los mecanismos de aislamiento del kernel podría permitir a un proceso escapar de los límites establecidos y acceder a recursos del sistema anfitrión. Por este motivo, aunque los contenedores proporcionan un nivel de aislamiento suficiente para numerosos escenarios de producción, la virtualización mediante máquinas virtuales puede proporcionar una frontera de aislamiento adicional al separar los sistemas operativos mediante el hipervisor.

 Por este motivo, también han surgido alternativas como las \textit{Library OS}(también conocidas como \textit{unikernels}) que proponen un modelo de ejecución diferente al de los contenedores. En este modelo, la aplicación se ejecuta junto con únicamente las librerías y componentes del sistema necesarios para su funcionamiento, integrados en una imagen especializada que dispone de los mecanismos mínimos necesarios para su ejecución. De esta forma, se reduce considerablemente la cantidad de componentes presentes en el entorno de ejecución y se puede alcanzar un mayor nivel de aislamiento respecto a un contenedor convencional.

 No obstante, los \textit{unikernels} presentan determinadas limitaciones que dificultan su adopción generalizada en entornos de producción. Entre ellas se encuentra la falta de una estandarización ampliamente adoptada para su construcción, ejecución, despliegue y gestión. Frameworks como \textit{NanoVMs}\footnote{\url{https://nanovms.com/}} y \textit{Unikraft} \footnote{\url{https://unikraft.com/}} han desarrollado herramientas y mecanismos orientados a facilitar estos procesos, aunque su adopción y ecosistema son todavía más reducidos que los existentes para las tecnologías de contenedores convencionales.

 Adicionalmente, la utilización de \textit{unikernels} dificulta la obtención de determinadas métricas relacionadas con el consumo energético. Al disponer únicamente de los componentes necesarios para ejecutar la aplicación y carecer de un sistema operativo Linux convencional, no se dispone de mecanismos como los \textit{cgroups} utilizados habitualmente para contabilizar y controlar el consumo de recursos de los procesos. Esto limita la aplicación directa de determinadas herramientas de monitorización energética desarrolladas para entornos Linux convencionales y supone una dificultad adicional a la hora de realizar mediciones comparables con las obtenidas en entornos basados en contenedores.

 Debido a las limitaciones que presentan actualmente los \textit{unikernels}, se selecciona el sistema de virtualización \textit{containers} de Docker para llevar a cabo el proceso de codificación/transcodificación de cada experimento de este proyecto de investigación.


\subsection{Codificación de Video sobre Contenedores}

Dada la arquitecura de los \textit{containers}, al hacer uso del mismo kernel que el sistema operativo estos pueden acceder a la capacidad de computo de los componentes del sistema, como la CPU o la GPU. Esta capacidad es esencial para llevar a acabo tareas exigentes en capacidad de computo que pueden extenderse a lo largo del tiempo, como la codificacion de video.

Para abilitar la acceleracion mediante hardware es necesario configurar el \textit{pass-through}, el cual esta compusto por dos elementos; el archivo de configuracion del sistema que contiene diversas funciones/ordenes que puede ejecutar sobre el sistema(a excepcion de algunas como read, open, etc...); Y descargar el descargar el \textit{runtime}, el cual consiste en una serie de librerias  que se comunican con los drivers del sistema para construir los contenedores, definiendo las propiedades del namespace y el cgroup al ejecutar el container \cite{hw-acceleration-container}. 

Cada uno de estos runtimes es gestionado por el proveedor del componente hardware al que se quiere acceder. Por defecto, docker utiliza Open Container Initiative (OCI)(empleando el runtiem \textit{RunC}) \cite{runtime-comparation}, por tanto es neceario descargar y configurar el runtime correspondiente al componente hardware sobre el cual se desea acceder. En el caso de necesitar acceso a la capacidad de computo de una GPU NIDIA, se debe de instalar el runtime de NVIDIA, e idicar que se emplee dicho runtime al crear el contenedor.
